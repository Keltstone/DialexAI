# GitLab CI/CD Integration & Pipeline Setup Guide

**Module:** `scribex-ai`  
**Platform:** GitLab SaaS & Self-Hosted GitLab CE / EE  
**Audience:** DevOps Engineers, GitLab Administrators, Release Engineers, Developers  
**Scope:** Merge Request gating pipelines, CI/CD templates, protected variables, binary verification, and self-hosted network configuration.

---

## 1. Overview & Operational Model

GitLab is widely deployed across enterprise and sovereign environments requiring strict data residency and on-premise governance.

Scribex AI integrates into GitLab CI/CD pipelines to:
1. **Gate Merge Requests:** Run `scribex check -base origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME` to ensure documentation matches code signatures before code merges.
2. **Lint Interlinked Wikis:** Run `scribex wiki lint` to catch broken links, missing backlinks, and orphan documentation pages.
3. **Protect Enterprise Credentials:** Ensure AI API tokens and Atlassian tokens are strictly isolated to protected branches.

---

## 2. Automated Pipeline Scaffolding (`scribex ci init gitlab`)

Initialize the GitLab CI configuration directly from the CLI:

```bash
scribex ci init gitlab
```

This creates `.gitlab-ci.scribex.yml` in your repository root.

Include this file in your main `.gitlab-ci.yml`:
```yaml
include:
  - local: '.gitlab-ci.scribex.yml'
```

## 3. GitLab Pipeline Configuration (`.gitlab-ci.scribex.yml`)

The template generated by Scribex is hardened for reproducibility and security:

```yaml
# Scribex GitLab CI Pipeline
# Stage: test
# Enforces documentation freshness on Merge Requests

stages:
  - test

scribex-check:
  stage: test
  image: golang:1.27.0@sha256:f92b6ef800e499660581efdabdf25d9d817a9d124eaf900924f0504e7e27e12d
  variables:
    GIT_DEPTH: "0"  # Requires full git history to compute diffs against target branch
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  before_script:
    - |
      if [ -n "$SCRIBEX_SRC" ] && [ -d "$SCRIBEX_SRC" ]; then
        echo "Building scribex from source: $SCRIBEX_SRC"
        (cd "$SCRIBEX_SRC" && go build -trimpath -buildvcs=false -ldflags "-s -w" -o /usr/local/bin/scribex ./cmd/scribex)
      elif [ -n "$SCRIBEX_RELEASE_URL" ] && [ -n "$SCRIBEX_SHA256" ]; then
        echo "Downloading scribex release binary..."
        curl -fsSL "$SCRIBEX_RELEASE_URL" -o /usr/local/bin/scribex
        echo "$SCRIBEX_SHA256  /usr/local/bin/scribex" | sha256sum -c -
        chmod +x /usr/local/bin/scribex
      else
        echo "Error: Set SCRIBEX_SRC (source directory) or SCRIBEX_RELEASE_URL and SCRIBEX_SHA256" >&2
        exit 1
      fi
  script:
    - scribex config validate
    - TARGET_BRANCH="$CI_MERGE_REQUEST_TARGET_BRANCH_NAME"
    - git fetch origin "$TARGET_BRANCH"
    - scribex check -base "origin/$TARGET_BRANCH"
    - scribex wiki lint
```

## 4. Binary Distribution Strategies in GitLab CI

Depending on your security and compliance requirements, choose one of two binary provisioning methods:

### Option A: Official Pre-Built Binary with Cryptographic Verification (Recommended)
Set the following GitLab CI/CD variables in **Settings** $\rightarrow$ **CI/CD** $\rightarrow$ **Variables**:

- `SCRIBEX_RELEASE_URL`: `https://github.com/Keltstone/DialexAI/releases/download/v1.0.0/scribex-linux-amd64`
- `SCRIBEX_SHA256`: `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` (Match official checksum)

The pipeline downloads the binary and verifies its SHA-256 digest before execution.

### Option B: Build from Source in Monorepo
If Scribex source code is checked into the same repository (e.g., monorepo setup):
- Set `SCRIBEX_SRC`: `scribex-ai` (relative path to source directory).

## 5. Secret Management & Fork Isolation

### Protecting Secrets from Fork Merge Requests
In GitLab, Merge Requests from forks can potentially execute arbitrary commands in CI. To protect your API credentials:

1. Navigate to **Settings** $\rightarrow$ **CI/CD** $\rightarrow$ **Variables**.
2. Add:
   - `ANTHROPIC_API_KEY` (or `OPENAI_API_KEY`)
   - `ATLASSIAN_TOKEN`
3. Configure attributes:
   - ☑️ **Masked:** Prevents secrets from being echoed in job logs.
   - ☑️ **Protected:** Ensures variables are only passed to pipelines running on protected branches (e.g., `main`, `production`).
4. **Result:** Untrusted feature branches and fork MRs never receive the secrets, while post-merge pipelines on `main` retain full access.

## 6. Self-Hosted GitLab & Private Network Configuration

When deploying on an on-premise GitLab instance (Omnibus or GitLab Helm Chart) inside a corporate intranet:

1. **Private Subnet Allowlist:**
   If Scribex needs to connect to internal services (self-hosted Jira, Confluence, or internal AI models):
   ```yaml
   scribex-check:
     variables:
       SCRIBEX_ALLOW_PRIVATE_HOSTS: "1"
   ```
2. **Corporate HTTP Proxy:**
   If your runners require an outbound HTTP proxy:
   ```yaml
   scribex-check:
     variables:
       HTTP_PROXY: "http://proxy.corp.internal:3128"
       HTTPS_PROXY: "http://proxy.corp.internal:3128"
       NO_PROXY: "gitlab.corp.internal,localhost,127.0.0.1"
   ```
   Scribex automatically respects standard proxy environment variables and runs pre-flight DNS checks before routing.

## 7. Troubleshooting & FAQ

### Q: `fatal: couldn't find remote ref refs/heads/...`
- **Cause:** GitLab runners default to shallow clones (`GIT_DEPTH: 20` or `50`), so the upstream target branch commit is not in local history.
- **Fix:** Set `variables: { GIT_DEPTH: "0" }` and execute `git fetch origin "$CI_MERGE_REQUEST_TARGET_BRANCH_NAME"`.

### Q: `scribex: impact gate: cannot prove no change in file.go`
- **Cause:** The git diff between head and base cannot be resolved cleanly due to shallow fetch or detached HEAD.
- **Fix:** Verify that `GIT_DEPTH: "0"` is active in your pipeline.
